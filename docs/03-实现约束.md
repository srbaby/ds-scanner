## 一、前端（改 `js/` 或 `index.html` 前必读）

### 1.1 前端脚本必须是普通 `<script>`，不能用 `type="module"`

`js/api.js` / `js/decision.js` / `js/app.js` 按顺序加载、共享同一全局作用域
（`app.js` 里直接用 `GistClient`/`parseJsonl`/`actionPriority` 等名字，不用 `import`）。

**为什么**：为了双击 `index.html` 用 `file://` 直接打开也能测，不强依赖起服务器。
2026-07-15 曾误改成 `type="module"`，`file://` 登录被 CORS **静默**弄坏，好几天没人发现。

### 1.2 改登录/连接链路，必须用真实 token+gist 走一遍成功路径

不能只看"控制台无报错"，也不能只测假 token。

**为什么**：假 token 会在 401 那步提前 return，根本走不到后面真正出错的代码，
造成"看起来修好了"的假象。2026-07-19 那次 `parseJsonl` 命名冲突死循环爆栈就是这么漏测的
（`app.js` 里一个同名本地函数覆盖了 `api.js` 的真实实现）。

### 1.3 往 HTML 属性里塞 `JSON.stringify(...)` 必须用 `escapeAttr`，不能用 `escapeHtml`

**为什么**：`escapeHtml` 只转义 `& < >`，**不转义双引号**；而 `JSON.stringify` 全是双引号，
值会在属性里被提前截断，`JSON.parse` 静默炸掉、`catch` 成 `{}`。

2026-07-19 发现 `js/app.js` 的 `data-reason="${escapeHtml(JSON.stringify(...))}"` 正是如此：
下拉框选项**看着完全正常**（可见文字是单独转义的），但背后存的理由数据全烂，
导致所有登记不论是否匹配上扫描器建议，最后都被兜底成 `rule_code: MANUAL_BACKFILL`。
这个 bug 从功能上线起就存在，2026-07-10/07-13/07-14 三笔交易的"人工补录"标签都是被它污染的，
已用 `CORRECT_REASON` 事件在 Gist 里更正。

**改任何 `data-*="${...}"` / `title="${...}"` 前，先确认塞进去的字符串会不会有引号。**

### 1.4 改前端加载方式或接口形状，必须同步改 `js/test_app.js` / `js/test_api.js`

**为什么**：这两个测试是 `scan.yml` 的**第一步**（`npm run test:frontend`）。它一红，
`ds_scanner.py` 根本跑不到——当天没 report、没 Bark、不写 Gist，而失败只体现在
Actions 历史里，**不会主动通知任何人**。2026-07-19 改回普通 script 后忘了改测试，
连挂 3 次才被发现。

两个测试用 `vm` 把三个脚本按 `index.html` 的顺序丢进同一 context 加载（复刻浏览器行为），
**不走 ESM `import`**——这些文件没有任何 `export`，用 `import` 必然 `SyntaxError`。

另注意两点：

- `test_app.js` 里那条 `type="module"` 的 guard 正则**必须限定在 `<script` 标签内**，
  因为 `index.html` 里解释"为什么不用 module"的注释本身就含这个字面量，全文搜会自己命中自己。
- `vm` 是独立 realm，跨 realm 的对象/数组原型不同，结构比较要用宽松 `deepEqual`，
  `deepStrictEqual` 会误报。

### 1.5 这些 CSS 类名是动态拼接的，纯文本搜索搜不到，别当死代码删

`js/app.js` 里用模板字符串拼类名，静态扫描会把它们全报成"零引用"。
2026-07-10 那次死代码扫描第一轮命中 23 个候选，人工复核排除了 20 个，全是这类：

| Class 前缀 | 拼接方式 |
| --- | --- |
| `.observer-line-{csi500,hs300,xplan,enhanced_ref}` | `` `observer-line-${line.key}` `` |
| `.observer-legend-*` / `.observer-tooltip-*` | 同上，`${line.key}` |
| `.quick-action-{buy,add,hold,sell,skip}` | `` `quick-action-${type}` `` |
| `.policy-watch-{risk,trigger}` | `` `policy-watch-${tone}` ``，`tone` 由调用方传 |
| `.execution-{corrected,reversed}` | `` `execution-${display.cls}` ``，来自 `eventDisplayState()` |

Python 侧同类陷阱：`sort_key`（`compare_policy_decision.py`）作为 `key=sort_key` 传给
`sorted()`，**不带括号**，搜 `sort_key(` 搜不到，但确实在用。

**删任何"看起来没被引用"的东西前，先确认它不是被拼出来的。**

### 1.6 桌面表格列宽按实测字符宽度定

`css/style.css` 的 `grid-template-columns` 是按实际内容量出来的，改前先用浏览器量，别拍脑袋。
2026-07-19 曾因"实仓→目标"列宽不够导致换行、把卡片撑高。

## 二、行情与政策数据链路

> 这一组的共同教训：**"静默降级成看起来正常的值"比直接报错危险得多。**
> 改数据链路时优先让异常可见，不要给一个"合理"的默认值。

### 2.1 行情历史不复权，份额折算会污染 MA20，且 T-1 校验查不出来

`ak.fund_etf_hist_sina` 没有 `adjust` 参数。份额折算日收盘价单日跳变几十个百分点，
只要断层落进 MA20 窗口，MA20 就被永久拉偏。而原有的 `close_gap_pct` 只比对**最后一根**
K 线与实时行情，**看不到窗口内部的断层**；唯一兜底是 `abs(MA20偏离) > 30` 这个拍脑袋阈值。

2026-07-27：半导体ETF 偏离 −29.64%，**差 0.36 个百分点漏网**被判"有效"
（同一现象的通信ETF −31.94% 被拦下）。后果是技术分被压到 4/25，
且"现价>MA20"这条开仓硬条件永远不可能满足——一只政策分满分 30/30 的 S 级标的被**静默除名**。

现由 `repair_price_discontinuity()` 前复权修正：单日跳变 >25% 即判定折算
（A股ETF涨跌停上限 20%，真实行情到不了这个量级），价格与成交量反向缩放。

⚠️ **结果记进 `data_quality.adjustments`，不是 `issues`**——`valid` 由
`not quality_issues` 决定，进 `issues` 会把标的直接判死，那跟原来的漏洞是同一个后果。

### 2.2 政策研判必须跑在扫描器之前，否则等于没接

`policy_research` 产出的主题 delta 是四维评分的输入
（`ds_scanner.load_policy_deltas()` 读 `snapshots/last_delta.json`）。

2026-07-27 之前，`scan.yml` 里政策步骤排在 `ds_scanner.py` **之后**，
`ds_scanner.py` 里也没有任何一处引用政策数据——`score_policy_delta.py` 老老实实算出的
`effective_base` 没有任何人读，政策对每日操作建议**零影响**，只在看板上当摆设。

**改 workflow 顺序时注意别改回去。**

### 2.3 三条命名链必须严格同名

```
theme_keywords.json 的主题名 → etf_base_config.json 的板块名 → etf_pool.json 的 category
```

任何一环对不上，政策 delta 就**静默落空**（既不报错也不告警）。
当前 22/22 完全对齐。**加新主题或新板块时三处一起加。**

### 2.4 政策事件的 `published_at` 必须来自源站，不能兜底成"今天"

采集端曾把 `published_at` 写死 `None`，抽取端再兜底成 `datetime.now()`；
叠加 Actions 里 `data/policy_research/events/` 每次都是全新目录（既不提交也不从 Gist 恢复），
等于每天把同一条事件重新标成"今天发布"——`age_days` 恒为 0、衰减权重恒为 1.0，
`score_policy_delta.py` 里整套半衰期/过期逻辑**全是死代码**。

2026-07-27 发现证券ETF那条"账户管理功能优化试点"从功能上线起一直挂在满权重不动，
`expires_at` 每天顺延（当天值 2026-09-25 = 当天 +60 天，**正是这个 bug 的指纹**）。

**2026-07-29 更正：那次只修了一半，病根还在，直到用户追问"为什么每次都是证券"才查出来。**

采集端确实不再造假了，但抽取端 `extract_policy_events.py` 仍然在
`published_at` 为 `None` 时兜底成 `datetime.now()`——只是多打了个
`published_at_estimated` 标记、把权重压到 0.5。**降权不解决不死的问题**：
0.5 权重但永不衰减 > 1.0 权重但 20 天半衰期，约 20 天后僵尸就反超了。

更要命的是**年龄护栏把事情弄反了**。那条试点公告的页面上白纸黑字写着
`证监会同意开展证券公司账户管理功能优化试点 2021-12-03`，**日期被正确解析出来了**，
却因为超过当时的 `MAX_PUBLISHED_AGE_DAYS = 1095`（3 年）被判为"没有日期"，
抽取端再兜底成今天。**护栏本意是拒绝垃圾日期，实际是把 4.6 年前的旧闻变年轻了。**

于是形成自然选择：日期真实的事件会衰减、过期、退出；日期兜底的每天重生成"今天"，
`expires_at` 天天顺延。**长期只有僵尸能活在 `active_delta` 里**——查出时 10 条事件
里 4 条兜底，而 3 个生效主题（证券+1 / AI算力−2 / 国防安全−1）**全部**由僵尸驱动，
日期真实的一条都没进。所以"每次都是证券"不是 1/15 的巧合，是接近必然。

现在的规矩：

1. **没有真实发布日期就不进评分**，直接排除并计入 `last_extract.json` 的
   `skipped_no_date`。排除数突增 = 某个源改版导致日期解析失效。
2. **旧日期照收**，交给半衰期/过期机制淘汰。只拒绝未来日期——解析错成旧日期是安全
   方向（会被判过期排除），错成未来则永不过期。
3. **列表页的月日（`07-24`）也要认**，且只认"整行就是个日期"的情形
   （`date_from_month_day` 看剔除标题后的残留字数）。光按总字数卡不住：
   `"3-5家公司参与本次试点安排并逐步扩大范围"` 才 22 字符，会把 `3-5` 读成 3月5日。
4. **认到日期就地返回，不再往上爬父容器**。爬一层就会看到兄弟条目的日期——
   证监会列表里"热轧卷板"那条自己写着 `07-24`，父容器里却先出现上一条的
   `2026-07-22`，爬上去就张冠李戴。

⚠️ **别把这类"下游还有一层兜底"的修复算作完成**。2026-07-27 那次改完采集端就收工，
测试 `test_event_without_publish_date_is_marked_estimated` 断言的正是兜底行为，
**把半截修复锁成了正确行为**，于是没有任何东西会报警。

⚠️ **事件目录仍是一次性的**（见 `05-未实现项.md`）。

### 2.7 "空壳数据"和"没有数据"必须可区分

修完 2.6 之后立刻发现的第二个洞：政策源**全部**采集失败时，`score_policy_delta.py`
照样无条件写出 `last_delta.json`（`as_of` = 今天、`themes` 全是空 delta），
扫描器判 `ok: True`，Bark 一声不吭——**和"采集正常、今天恰好没有政策事件"完全同形**。
2.6 加的可见性只覆盖了"文件缺失/过期"，覆盖不到"文件在、内容是空壳"。

现在 `collect_all()` 落盘 `source_total` / `all_sources_failed`
（**只记 `error_count` 没用**：区分不了"3 个源挂了"和"总共 3 个源全挂了"），
`score_policy_delta.source_health()` 把它透传进 `last_delta.json`，
`ds_scanner.load_policy_deltas()` 见到 `all_sources_failed` 直接判 not ok。

阈值上的取舍：

- **全源失败 = 故障**，扫描器拒用 + Bark 报警
- **采集 0 条新条目 ≠ 故障**。`collected_count` 统计的是去重后的新增，
  周末政务站不发文时天然为 0，拿它当信号会天天误报
- **零事件 ≠ 故障**，同上
- `last_delta.json` **没有 `source_health` 字段时按正常放行**（向后兼容旧产物），
  真正的陈旧数据由 `POLICY_DELTA_MAX_AGE_DAYS = 3` 拦

⚠️ 两处退出码（`collect_policy_news.main()` / `run_policy_research.main()`）也已改诚实
（原来 `error_count >= 0` 是恒真式，全源 403 也返回 0），但**别指望它自己会喊**：
政策步骤是 `continue-on-error`，非零退出照样被吞、Actions 照样全绿。
退出码只对本地跑和将来去掉 `continue-on-error` 有用，报警靠的还是上面那条 Bark 链路。

⚠️ **不要给 `test_policy_research.py` 补 compare 的导入**，会报
`ImportError: attempted relative import beyond top-level package`：该文件把
`automation/` 塞进 `sys.path` 再 `from policy_research import ...`，
而 `compare_policy_decision.py` 的 `from .. import ds_scanner` 越过了顶层包边界。
compare 只能以 `automation.policy_research.compare_policy_decision`
（仓库根在 `sys.path`）的姿势导入。`compileall` 已经把这一类问题堵死，
不必为此重构导入结构。

## 三、持仓登记的"三态"匹配（`js/app.js`）

网页登记买卖时，会把当日 `dashboard.json.decision.operations` 里的扫描器建议
和用户输入的代码/动作做匹配，三种结果：

| 状态 | 条件 | 行为 |
| --- | --- | --- |
| **匹配上** | 数据是今日的且找到对应代码/动作 | 正常放行，理由标签用扫描器的 `rule_code`/`ai_action_id`，`data_confidence: scanner_authoritative` |
| **确无信号** | 数据是今日的但确实没有该代码/动作 | 允许人工补录（点"转人工补录"+`confirm()` 二次确认），`rule_code: MANUAL_BACKFILL`，`data_confidence: manual` |
| **数据不新鲜** | 没刷新成功／不是今日的 | **拦截**，下拉框禁用 |

**为什么第三态要拦截**：不能让用户在"数据没刷出来"的状态下被当成"确认无信号"而人工补录——
那会把一次数据故障记成一次人工决策，污染台账归因。

⚠️ `lastScanStatus`（`{ok, fresh, reason, generatedDate}`）**只在浏览器内存里**，
不落盘、不进 Gist。出问题无法事后反查，只能看当时下拉框旁边那行状态小字。

## 四、版本治理

`VERSION.json` 是统一版本清单。`validate_document_versions()` 会校验
`X-Plan.md` 的一级标题与 `Prompt.md` 的"方法论版本"行是否与清单一致，**不一致直接抛错**。

升版本要同步改的地方：

```
VERSION.json          methodology_version
X-Plan.md             一级标题 "# X-Plan vX.Y"
Prompt.md             "> 方法论版本：vX.Y"
X-Plan.md 模块12       版本记录表加一行
```

测试里**不要硬编码版本号**——断言引用 `versioning.METHODOLOGY_VERSION`，
或用 `^v3\.\d+$` 这类族匹配。2026-07-27 升 v3.2 时曾因 3 处硬编码断言全红。

升级判据（X-Plan 模块12）：改核心交易逻辑升主版本，微调升小数位。
**改了 `X-Plan.md` 就要升版**。
