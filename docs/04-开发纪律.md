# 第四篇 · 开发纪律

> 提交前对照本篇检查。

---

## 4.1 审查方法论（三步验证）

给出"这是个缺陷"的结论前，必须完成：

1. **业务验证**：对照 `01-业务意图.md`，确认是否符合业务预期。
   结构看似异常的代码可能是有意设计（如零信号日、政策不碰止损、空仓是常态）。
2. **数据验证**：基于真实数据，不允许用假设场景推断。
   本项目线上状态在 Gist，可用 `gh api gists/<id>` 直接读——**先去看真数据**。
3. **影响范围验证**：区分"逻辑看起来不一致"和"结果确实有误"。

**给出缺陷结论前必须能回答：在什么场景下，用户会看到什么错误结果。答不出不算确认的缺陷。**

---

## 4.2 改动原则

- **读再动**：先读懂现有代码，不靠猜测。
- **改原处，不包裹**：找到根源直接改，不在外部套新函数绕开原代码。
- **不许包裹式膨胀**：约束的是"加 if 绕开症状、留以后可能用得上的死变量、
  保留不工作的僵尸函数"。**新增真实能力可以净增行数，但要如实报数。**
  （一条无法诚实满足的规则只会诱导执行者去伪造合规证据。）
- **不擅自补功能，但鼓励提议**：审查只报问题；觉得缺功能 → **说出来、给建议、等裁决**，不动手。
  执行已批方案时发现方案本身有缺口，属于提议范畴——**提出来，别默默补也别默默跳过**。
- **结构性改动先问**：目录结构、文件清单、跨层方案、删除疑似有用的函数。
- **删除代码/文件由大亨拍板**：本仓库既有约定。可以给出规格与依据，不擅自执行。

---

## 4.3 测试纪律

1. **前端测试是第一道门禁，也是最容易忘的一道。** 改前端加载方式或接口形状，
   必须同步改 `js/test_app.js` / `js/test_api.js`，否则当天整个扫描不跑
   （详见 `03-实现约束.md` 1.4）。
2. **改数据链路必须补回归测试**，且测试要覆盖**降级路径**——
   本项目的事故几乎全是"静默降级成看起来正常的值"，只测正常路径抓不到。
3. **测试里不硬编码版本号**（见 `03-实现约束.md` 第四节）。
4. **跨 realm 比较用宽松 `deepEqual`**，`deepStrictEqual` 会误报。
5. 本地没有 pandas 时，建临时 venv 跑，别动系统 Python。

## 4.4 涉及真实交易决策的改动

**本系统的输出会变成真实买卖。** 改到下列任一处，视同高风险：

```
四维评分的任何一维
B/A/S 分级门槛
止损/止盈/清仓规则
仓位档位与上限
政策 delta 的幅度或作用范围
scan.yml 的步骤顺序
```

要求：

- 先改 `X-Plan.md`（canonical），再改代码——**不许代码先行、文档追认**。
- 升方法论版本（见 `03-实现约束.md` 第四节）。副作用是好事：
  `stats.json` 会按版本分组统计，新旧行为的表现能分开评估。
- 端到端验证一次，且**用真实配置**，不能只跑单测。
- 交付说明里写清**边界**：这个改动不能做什么（例如"政策不能触发止损、
  不能绕开量比与 MA20 硬条件"）。

## 4.5 文档纪律

- **规则只在 `X-Plan.md`。** 任何地方不得复述交易规则——包括"速查索引"这类看似无害的摘要。
  2026-07-27 删掉的那张索引表就是反例：v3.0 重写时没同步，10 个概念烂了 9 个，
  模块号几乎全错，而**它烂掉的方式看不出来**。
- **业务意图只在 `01`。** "为什么这么设计"只有一个出处。
- **反直觉实现双写**：代码注释 + `03-实现约束.md`，且注明为什么。只写一边等于没写。
- **不留归档副本**：改文档就直接改，历史交给 git。
  ```bash
  git log --oneline -- docs/01-业务意图.md
  git show <hash>:docs/01-业务意图.md
  ```
- **发现文档与代码冲突，默认代码对、文档漏**——先问，不要按文档去"修正"代码。
  2026-07-27 那次 AI 描述失实就是典型：`js/app.js` 早已正确处理 `enabled:false`，
  烂的是 CLAUDE.md。
