> **这是判断"这段代码 / 这个数字是不是有意设计"的唯一依据。**
> 规则**怎么执行**看 `X-Plan.md`（canonical，唯一规则源）；本篇只讲**为什么这么设计**、

## 一、这个系统解决什么问题

**用户是上班族，交易日白天在工作，没有盯盘条件。**

由此推导出的全部约束：

| 约束 | 由此产生的设计 |
| --- | --- |
| 白天不能看盘 | 每天**只有一次**决策窗口（尾盘 14:49 扫描 → 14:55-15:00 执行） |
| 不能盘中反应 | 系统输出**目标仓位**而非买卖点；错过当天就等明天，不追 |
| 主观决策容易被情绪带偏 | 决策由扫描器**确定性计算**，人只做执行与否决，不做打分 |
| 决策要能事后复盘 | 每笔交易必须沉淀结构化依据（规则代码、信号等级、当时各项指标） |
| 上真钱前要有底 | 先用影子盘跑，攒够证据再谈转实盘 |

**它不是选股软件，也不是荐股系统。** 它是一台"每天替你把 18 只 ETF 过一遍筛子、
给出今天每只应该持有多少"的机器。核心问题不是"买不买"，而是"今天该是 0/10/15/20 哪一档"。

**它是影子交易实验系统**，与用户主投资体系（0号/1号的 PE 体系、铁律、持仓）**完全隔离**：
本系统的持仓、信号、分数不写入主体系文档，主体系的仓位纪律也不约束本系统。
两边混谈会同时污染两套决策。

## 二、两个子系统（复杂度的来源，必须分清）

**这是理解本项目的关键。** 现行版本是 2.x 的升级，在原有的"扫描研判"之外
**新增了一整套"验证评估"**，项目复杂度主要来自这里。两者目标不同、数据不同、失败后果也不同。

### A. 扫描研判系统（决策生成）— 2.x 就有，是主干

**它回答：今天该怎么操作？**

```
政策事件研判 → 行情扫描 → 四维评分 → B/A/S 分级 → 目标仓位 → 操作清单
```

- 产出：`decision.json`（结构化权威决策）、`report.txt`（人读的报告）
- 送达：Bark 推送全文 + 网页看板
- **权威性**：扫描器的操作清单就是当日终局结果。AI 只做非权威审计，不得覆盖决策。
- 失败后果：**当天没有操作建议**。属于"少赚"，可接受。

### B. 验证评估系统（观察器）— 3.x 新增，是这次复杂度的来源

**它回答：这套方法论到底有没有用？该不该上真钱？**

```
交易台账 → 净值快照 → 与基准对比 → 胜率/盈亏比/回撤 → 毕业与熔断进度
```

- 产出：`trades_<年>.jsonl`、`portfolio_snapshots_<年>.jsonl`、`stats.json`、`observer_state.json`
- 送达：网页的量化观察面板
- **它不参与任何交易决策**——观察器算出来的任何数字都不会反过来改变明天的操作建议。
- 失败后果：**统计失真，可能导致错误的"能不能上真钱"判断**。比"少赚"严重。

### 为什么必须分清

新会话最容易犯的错，是把 B 的数字当成 A 的依据（或反过来）：

- `stats.json` 里的胜率、收益、毕业进度，**回答的是"方法论行不行"，不是"今天买什么"**。
- `decision.json` 里的评分、信号等级，**回答的是"今天怎么操作"，不构成业绩证明**。

**改 A 要担心当天没建议；改 B 要担心几个月后基于错数字做出上真钱的决定。**

## 三、关键数字回答什么问题

同一个系统里有好几个"分"，含义完全不同。下表是它们的语义边界：

| 字段 | 回答什么问题 | 取值 | 谁产出 | **不能拿它干什么** |
| --- | --- | --- | --- | --- |
| `base_score` | 这个板块的政策环境有多友好？ | 0-15 | 人工维护 `etf_base_config.json` + 政策事件运行时偏移 | 不能直接当信号强度 |
| `score.policy_catalyst` | 四维评分里政策这一维得几分？ | 0-30 | `base_score × 2` | 不能与下面的 `policy` 混用 |
| `policy`（policy 总分） | 这只标的的持仓逻辑还成不成立？ | 0-30 | base+tech+strength，见 X-Plan 模块11 | **与四维评分无关**；它跌破 15 才触发 RISK_STOP |
| `score.total` | 今天这只标的综合有多强？ | 0-100 | 四维相加 | 分高不等于能买——还要过量比/MA20 硬条件 |
| `signal_grade` | 今天够不够开仓，够哪一档？ | 无效/B/A/S | 扫描器 | — |
| `data_quality.valid` | 这只标的今天的数据能不能用来做决策？ | 布尔 | 扫描器 | — |
| `data_quality.adjustments` | 数据修过什么？（如份额折算复权） | 列表 | 扫描器 | **有值不代表数据无效**，是"已修好并留痕" |
| `stats.summary.win_rate_pct` | 方法论的胜率 | % | 观察器 | 不能拿来调仓位 |
| `graduation.*` | 离"可以考虑上真钱"还有多远 | 进度% | 观察器 | 见下方第五节第 3 条 |

**最容易搞混的一对**：`policy`（0-30 的持仓逻辑分，管止损）和 `score.policy_catalyst`
（0-30 的四维政策位，管开仓评分）。名字像、量纲一样、含义完全不同。
X-Plan 模块11 专门写了一句"不能混用"，就是为这个。

## 四、有意为之（看着像缺陷，其实不是）

> 这一节是本篇存在的主要理由。**动这些东西之前先读完这里。**

### 1. 绝大多数交易日没有任何操作建议，这是正常输出

系统平均资金利用率约 15%（上限 65%），意味着**约 85% 的资金常年闲置**。
零信号日（`SKIP_NO_SIGNAL`）是最常见的输出，不是故障。

**业务理由**：这是一套"右轮"（右侧）系统，只在趋势与量能同时确认后才进场。
不追反弹第一棒是设计目标，不是保守。同期沪深300全收益 −0.16%、中证500全收益 −7.49% 的环境下，
本系统 +5.51%、最大回撤 −2.25%——**空仓正是超额收益的来源**。

⚠️ **但 X-Plan 模块6「资金利用反馈」规定**：胜率持续 >70% 而总仓位长期 <30%，
属于需要复查的方法论反馈信号。**当前状态已满足该触发条件**（胜率 78.95%、平均仓位 15.54%），
按方法论应检查"强信号开仓是否过小 / 确认加仓是否过严 / 盈利钝化是否过早 / 换仓是否过保守"。
**这条是方法论自带的，不是外部批评。**

### 2. 毕业进度沿用全期历史数据，是刻意的观察口径

`graduation.condition_a_progress_pct` 目前 100%、状态 `milestone_reached`。
其计算口径（滚动3月超额沪深300 ≥5%）覆盖**全部**历史交易，其中绝大部分产生于
v3.1 方法论上线（2026-07-09）之前的人工决策期。

**用户已明确：这个口径沿用历史数据，仅作观察，用户本人清楚其含义。**

因此：

- **不要**把它改成"只统计 v3.1 之后"——那是用户已经知晓并接受的取舍。
- **不要**把亮起的 `milestone_reached` 当成"可以转实盘"的系统结论。
  它是一个观察指标，转实盘是人的决定。
- 若未来要做严格的方法论验证，应**另起口径**（新增字段），而不是改这个。

### 3. 政策事件不能触发也不能压制止损

政策事件产生的主题偏移（±2）只叠加到 `base_score` 上，进四维评分的政策催化位。
**它完全不碰 `policy` 总分**，因此不可能影响 RISK_STOP。

**业务理由**：政策是"是否值得买"的输入，不是"是否该跑"的输入。
新闻可以让你多看一眼某个板块，但不该让你在该止损时不止损、或在不该止损时被吓出来。
同理，政策偏移也**不能绕开量比 / 现价>MA20 等硬条件**——它只能在既有信号上加减分，不能凭空造信号。

### 4. AI 不做决策，但 v3.3 起参与政策事件的归类

分清两件事，别混谈：

| | 现状 |
| --- | --- |
| **决策**——评分、信号等级、操作、目标仓位 | 扫描器确定性计算，唯一权威。AI 看不到也不产出 |
| **每日审计**——事后挑错 | `AI_PROVIDER` 默认 `none`，**未启用** |
| **政策事件归类**——归到哪个板块、利好还是利空 | **v3.3 起由 AI 判定**（`X-Plan.md` 模块11） |

政策 delta 是四维评分的输入，所以**AI 已经在决策链的上游**了。这是有意的取舍，
不是疏漏：原来的关键词规则太粗，标题里出现"消费税"就归到消费，哪怕讲的是电池消费税。

**"不可复现"这条顾虑还在，用四件事压住**：

```text
temperature=0，同样的输入不该今天判 + 明天判 −
每条事件留标题 + 原文链接 + 发布日期 + 贡献分值，看板可逐条穿透核对
AI 挂了整体退回关键词兜底，并在 report 与 Bark 显式标注——绝不静默
偏移夹紧在 ±2（四维总分最多动 4 分），不足以单独制造信号
```

换句话说：**可复现性的要求没有放弃，而是从"不用 AI"改成了"用了也要能逐条查证、
且失败必须显眼"。** 系统的目标仍是验证方法论，所以任何进决策链的环节都必须可归因。

### 5. Bark 推送全文，明知可能被截断

推送把 `report.txt` 全文塞进 body。APNs 单条 payload 约 4KB 上限，超长会被截断。

**业务理由**：用户的实际使用场景是"收到推送 → 长按复制全文 → 必要时手工喂给 AI 做二次分析"。
摘要式推送会切断这条兜底路径。**已知取舍，选择全文优先。**

### 6. 前端不用 ES module

`js/` 下的脚本按顺序加载、共享全局作用域，不用 `import`。

**业务理由**：为了双击 `index.html` 用 `file://` 直接打开就能测，不强依赖起服务器。
改成 module 会让 `file://` 因 CORS 静默失效。

### 7. 只有 18 只 ETF，且不预设同类互相确认

ETF 池是精选代表池。半导体涨不作为科创50的确认信号。

**业务理由**：池子小是为了让每只标的的政策基础分能被人工认真维护。
相关标的互相确认会制造虚假的信号密度。

## 五、数据真理源

**线上状态的唯一真理源是 Gist**（Description: `ds_scanner`）。

| 想知道 | 看哪 |
| --- | --- |
| 当前持仓、可用资金 | Gist `holdings.json` |
| 今天的决策与评分 | Gist `dashboard.json` |
| 方法论表现统计 | Gist `stats.json` |
| 交易台账 | Gist `execution_events_<年>.jsonl` / `trades_<年>.jsonl` |

**本地仓库的 `data/*.json` 是历史快照，不可据此判断当前状态。**
唯一仍需本地手工维护的是 `data/etf_base_config.json`（改完 push 生效）。

**交易台账 append-only，从不原地改历史。** 纠错靠追加 `CORRECT_REASON` 事件，
撤销靠追加 `REVERSE_EVENT`，展示层把最新更正盖在原记录上。
**业务理由**：影子盘的全部价值就是那份可信的历史。能被改写的台账等于没有台账。

## 六、明确不做的事

- **不做盘中多次调仓**：一天一次决策，错过等明天。
- **不做浮亏补仓**：加仓只允许右轮强势确认。
- **不自动执行交易**：系统只出清单，下单永远是人工动作。
- **不把政策 delta 回写 `etf_base_config.json`**：人工基础分是唯一手工真理源，自动化只在运行时加偏移。
- **不让 AI 修改评分或操作**。
- **不为提高样本量而放松硬门槛**：那会同时污染验证与风控。

## 七、当前已知的业务层面待决事项

记录备查，**不擅自处理**：

- **样本积累速度与验证目标不匹配**：v3.1 上线至今 13 个交易日仅产出 1 个开仓信号。
  按此速率攒到统计显著需约 18 个月。是否引入"影子记账"（不动真钱、只记虚拟交易以积累统计量）待决策。
- **出场几何不对称**：开仓要求现价 > MA20（常常刚刚站上），而 TREND_BREAK 在跌破 MA20 即触发，
  盈利侧出场线在入场时距离约 1%；亏损侧 RISK_STOP 在 −8%。实测 TREND_BREAK 平均 +2.07%、
  RISK_STOP 平均 −7.05%。该参数组合隐含要求约 77% 胜率才能打平。是否调整待决策。
- **盈亏比 0.6467 < 1**：系统靠高胜率而非高赔率盈利，盈亏平衡胜率 60.7%。
  当前胜率 78.95%（n=19），Wilson 95% 置信区间 [56.7%, 91.5%]，下沿低于平衡线——
  **现有样本尚不足以在统计上确立边际优势**。这是样本量问题，不是方法论已被证伪。
